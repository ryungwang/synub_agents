# Synub 운영 콘솔 매뉴얼

## 문서 목적

이 문서는 `synub_agents` 운영자가 Synub 운영 콘솔에서 직원 권한, 프로젝트, 오류 접수, 작업 검토, 승인, 실행, 감사 로그를 관리하는 방법을 설명한다.

직원용 데스크톱 앱 사용법은 앱 레포의 `docs/USER_MANUAL.md`를 기준으로 한다. 이 문서는 운영자 웹 콘솔만 다룬다.

## 접속과 로그인

로컬 운영 주소:

```text
http://127.0.0.1:3002
```

API 주소:

```text
http://127.0.0.1:8080
```

`ADMIN_TOKEN`이 설정되어 있으면 첫 화면은 로그인 페이지다. 로그인 입력값은 로컬 `.env`의 `ADMIN_TOKEN` 값과 같아야 한다.

로그인 후 새로고침했을 때 다시 로그인 페이지로 이동하면 다음을 확인한다.

- 브라우저에 저장된 관리자 토큰이 현재 `.env`의 `ADMIN_TOKEN`과 같은지
- API가 `http://127.0.0.1:8080`에서 실행 중인지
- 웹이 `http://127.0.0.1:3002`에서 실행 중인지
- 401 응답이 아닌 정책성 400/403 응답을 로그인 만료로 오해하고 있지 않은지

## 로컬 실행

### macOS

H2 파일 DB:

```bash
./infra/scripts/start-local.sh
```

PostgreSQL:

```bash
./infra/scripts/start-local.sh --postgres
```

워커 포함:

```bash
./infra/scripts/start-local.sh --postgres --with-worker
```

중지:

```bash
./infra/scripts/stop-local.sh
```

스크립트 권한 오류가 나면 다음을 한 번 실행한다.

```bash
chmod +x infra/scripts/*.sh
```

### Windows

H2 파일 DB:

```powershell
.\infra\scripts\start-local.ps1
```

PostgreSQL:

```powershell
.\infra\scripts\start-local.ps1 -Postgres
```

워커 포함:

```powershell
.\infra\scripts\start-local.ps1 -Postgres -WithWorker
```

중지:

```powershell
.\infra\scripts\stop-local.ps1
```

## 기본 운영 흐름

1. `관제 현황`에서 GitHub, API, 웹, 워커 상태를 확인한다.
2. `직원 권한`에서 직원을 등록하고 앱 라이선스를 부여한다.
3. `프로젝트 설정`에서 프로젝트와 멤버 권한을 준비한다.
4. `AI 직원 구성`에서 역할별 AI 직원을 확인한다.
5. `오류 접수`에서 직원 앱 제보 이슈를 검토한다.
6. 실행 가능한 이슈에 `codex-ready` 라벨을 붙이거나, 콘솔에서 라벨 처리를 한다.
7. `작업 검토`에서 작업 생성 가능 여부, 위험도, 담당 AI 직원을 확인한다.
8. 고위험 작업은 `승인 대기`에서 승인한다.
9. `실행 관리`에서 워커 실행, 실패 재시도, 로컬 서비스를 관리한다.
10. `감사 로그`에서 누가 어떤 작업을 처리했는지 확인한다.

## 메뉴 구조

현재 운영 콘솔 메뉴는 다음 순서로 사용한다.

| 구분 | 메뉴 | 목적 |
| --- | --- | --- |
| 운영 | 관제 현황 | 전체 상태 요약과 당일 운영 흐름 확인 |
| 준비 | 직원 권한 | 직원 등록, 앱 라이선스 부여/회수 |
| 준비 | 프로젝트 설정 | 프로젝트, 멤버, 중앙 작업 요청 관리 |
| 준비 | AI 직원 구성 | 역할별 AI 직원과 담당 키워드 확인 |
| 처리 | 오류 접수 | 직원 앱 오류 제보 이슈 검토 |
| 처리 | 작업 검토 | 작업 실행 생성 전 최종 검토 |
| 처리 | 승인 대기 | 고위험 작업 승인 처리 |
| 처리 | 실행 관리 | 작업 실행 이력, 재시도, 워커 제어 |
| 기록 | 감사 로그 | 운영 변경 이력 추적 |
| 기록 | 시스템 설정 | GitHub 연결, 로컬 서비스 상태 확인 |

## 운영 > 관제 현황

### 목적

`관제 현황`은 운영자가 가장 먼저 보는 화면이다. GitHub 연결, 로컬 워커, 작업 요청, 실패 실행 수를 한 화면에서 확인한다.

### 확인 항목

- GitHub 저장소가 설정되어 있는지
- `codex-ready` 라벨 동기화가 가능한지
- 워커가 실행 중인지
- 대기 중인 작업과 승인 대기 작업이 있는지
- 실패 실행이 누적되고 있는지

### 권장 처리

- GitHub가 `미설정`이면 `시스템 설정`에서 토큰과 저장소 환경변수를 확인한다.
- 워커가 중지되어 있으면 `실행 관리`에서 워커를 시작한다.
- 실패 실행이 있으면 `실행 관리`의 재시도 정책을 먼저 확인한다.
- 정보 부족, 테스트성 이슈는 작업 실행 대상으로 넘기지 않는다.

## 준비 > 직원 권한

### 목적

직원용 앱은 누구나 설치해서 쓰는 구조가 아니다. 관리자가 직원 ID를 등록하고 라이선스를 부여한 직원만 앱에 진입할 수 있다.

### 직원 등록

1. 직원 이름을 입력한다.
2. 직원 ID를 입력한다.
3. 역할을 선택한다.
4. 이메일을 입력한다.
5. 등록한다.

직원 ID는 직원 앱 로그인에 사용되므로 운영 중 바꾸지 않는 것을 원칙으로 한다.

### 라이선스 부여

1. 등록된 직원 목록에서 대상 직원을 확인한다.
2. `부여`를 누른다.
3. 상태가 `사용 가능`으로 바뀌었는지 확인한다.
4. 직원에게 중앙 API 주소와 직원 ID를 전달한다.

### 라이선스 회수

1. 대상 직원의 `회수`를 누른다.
2. 상태가 회수 상태로 바뀌었는지 확인한다.
3. 회수된 직원은 새 인증 또는 앱 재실행 시 앱 사용이 차단된다.

### 운영 기준

- 퇴사자, 외주 종료자, 임시 접근자는 즉시 회수한다.
- 라이선스는 앱 사용 권한이고, 프로젝트 접근은 프로젝트 멤버 권한으로 별도 관리한다.
- 권한 변경은 감사 로그에 남는지 확인한다.

## 준비 > 프로젝트 설정

### 목적

중앙 프로젝트와 프로젝트별 멤버 권한, 중앙 작업 요청을 관리한다.

### 프로젝트 등록

1. 프로젝트 이름을 입력한다.
2. 저장소를 입력한다.
3. 작업 디렉터리 경로를 입력한다.
4. 프로젝트 설명을 입력한다.
5. 저장한다.

작업 디렉터리 경로는 워커가 실제로 Codex를 실행할 위치다. 경로가 틀리면 작업이 실패한다.

### 멤버 권한

1. 프로젝트를 선택한다.
2. 직원 목록에서 멤버를 추가한다.
3. 역할을 지정한다.
4. 필요 시 권한을 회수한다.

직원이 라이선스를 가지고 있어도 프로젝트 멤버가 아니면 해당 프로젝트 작업 요청을 제한하는 방식으로 운영한다.

### 중앙 작업 요청

운영자가 직접 프로젝트 작업 요청을 만들 수 있다.

1. 프로젝트를 선택한다.
2. 요청자를 선택한다.
3. 작업 제목을 입력한다.
4. 요청 내용을 구체적으로 작성한다.
5. 요청을 등록한다.

요청 내용에는 재현 절차, 기대 동작, 영향 범위, 관련 화면 또는 파일을 포함한다.

## 준비 > AI 직원 구성

### 목적

작업이 어떤 AI 직원에게 배정되는지 확인한다. 백엔드, 프론트엔드, QA, 문서, 운영 역할이 언어와 작업 키워드 기준으로 세분화되어 있어야 한다.

### 확인 항목

- 백엔드 역할이 Java, Spring, API, DB, migration 키워드를 담당하는지
- 프론트엔드 역할이 TypeScript, React, CSS, UI, routing 키워드를 담당하는지
- QA 역할이 test, regression, bug, repro 키워드를 담당하는지
- 문서 역할이 manual, docs, README, checklist 키워드를 담당하는지
- 운영 역할이 deploy, script, local service, worker 키워드를 담당하는지

### 운영 기준

- 작업 배정이 이상하면 작업 실행 전에 담당 AI 직원을 확인한다.
- 특정 언어 작업이 계속 잘못 배정되면 AI 직원 구성 데이터를 보강한다.
- 신규 기술 스택이 들어오면 키워드를 추가한다.

## 처리 > 오류 접수

### 목적

직원 앱에서 접수된 GitHub `bug` 이슈를 운영자가 검토한다.

### 이슈 분류

| 분류 | 처리 |
| --- | --- |
| 재현 정보 충분 | `codex-ready` 후보 |
| 정보 부족 | 추가 정보 요청, 작업 생성 차단 |
| 단순 테스트 | 작업 생성 차단 |
| 중복 이슈 | 기존 이슈 링크 후 종료 |
| 민감 정보 포함 | 내용 삭제 또는 비공개 처리 |
| 고위험 변경 | 승인 절차로 이동 |

### 작업 실행 생성 기준

작업 실행을 만들 수 있는 이슈는 최소한 다음 중 하나 이상을 포함해야 한다.

- 재현 절차
- 실제 오류 메시지
- 기대 동작
- 영향 화면 또는 기능
- 관련 파일, API, 로그 경로

다음 이슈는 작업 생성하지 않는다.

- `테스트`, `test`, `샘플`, `임시`처럼 검증용으로 보이는 이슈
- 기본 템플릿 문구만 남은 이슈
- 오류 메시지와 재현 절차가 모두 없는 이슈
- 작업 범위가 너무 넓거나 제품 결정이 필요한 이슈

### 라벨 처리

콘솔에서 처리 가능한 항목은 `codex-ready` 라벨을 붙인 뒤 동기화한다. GitHub 웹에서 직접 라벨을 붙여도 되지만, 운영 콘솔에서 처리하면 감사 로그를 함께 남기기 쉽다.

## 처리 > 작업 검토

### 목적

`codex-ready` 이슈나 중앙 작업 요청이 실제 워커 실행으로 넘어가기 전에 최종 검토한다.

### 화면 구성

- 실행 가능 작업
- 생성 불가 작업
- 선택 실행 생성
- 단건 실행 생성
- 작업 상세

### 실행 가능 작업

다음 조건을 만족하면 실행 가능 작업으로 본다.

- 정보 부족 또는 테스트성 차단 사유가 없다.
- 이미 활성 실행이 중복으로 만들어져 있지 않다.
- 고위험 작업이면 승인 조건을 충족했다.
- 저장소와 담당 AI 직원이 확인되어 있다.

### 생성 불가 작업

생성 불가 작업은 별도로 확인한다. 생성 불가 사유가 표시되면 같은 항목을 반복 실행하지 말고 원인을 해결한다.

주요 사유:

- 기본 템플릿 또는 진단 정보 누락
- 테스트성 이슈
- 승인 필요
- 이미 실행 생성됨
- 저장소 또는 작업 디렉터리 정보 부족

### 일괄 처리

1. 실행 가능 항목 전체 선택을 누른다.
2. 선택 목록을 검토한다.
3. 위험도가 높은 항목이 섞여 있는지 확인한다.
4. 선택 항목 실행 생성을 누른다.
5. 각 항목 아래 성공/실패 메시지를 확인한다.

실패 메시지가 표시된 항목은 같은 버튼을 반복해서 누르지 말고 실패 사유를 먼저 해결한다.

## 처리 > 승인 대기

### 목적

고위험 작업이나 운영자 확인이 필요한 작업을 사람 승인 후 실행으로 넘긴다.

### 승인 대상 예시

- 인증/권한 변경
- 결제, 라이선스, 보안 정책 변경
- DB migration
- 배포 스크립트 변경
- 대량 삭제 또는 데이터 변환

### 단건 승인

1. 승인 대기 항목을 선택한다.
2. 작업 내용, 위험도, 저장소를 확인한다.
3. 승인 또는 보류를 선택한다.
4. 처리 결과가 감사 로그에 남는지 확인한다.

### 일괄 승인

1. 일괄 처리 모드에서 항목을 선택한다.
2. 같은 성격의 작업만 묶는다.
3. 승인 처리한다.
4. 처리 완료 영역에서 결과를 확인한다.

서로 다른 위험 범위의 항목은 일괄 승인하지 않는다.

## 처리 > 실행 관리

### 목적

워커 실행 이력, 실패 작업 재시도, 로컬 서비스 제어를 한 화면에서 관리한다.

### 작업 실행

작업 실행 영역에서는 최근 실행 이력을 확인한다.

확인 항목:

- 작업 ID
- 실행 명령
- 상태
- 실패 메시지
- PR 생성 여부

실패 메시지는 원인 분석의 기준이다. 예를 들어 `기본 템플릿 또는 진단 정보 누락`은 작업 내용 보강이 필요하다는 뜻이고, `workspace has uncommitted changes`는 작업 디렉터리 정리가 필요하다는 뜻이다.

### 재시도

재시도는 실패 상태인 작업 중 정책상 가능한 항목만 허용한다.

재시도 가능:

- 최신 실행이 실패 상태
- 실패 원인이 일시적 실행 오류
- 작업 디렉터리가 깨끗함
- 정보 부족 또는 테스트성 차단 사유가 없음

재시도 불가:

- 실행 중인 작업
- 정보 부족 이슈
- 테스트성 이슈
- 고위험인데 승인되지 않은 작업
- 작업 디렉터리에 커밋되지 않은 변경이 있는 작업

재시도 불가 사유가 표시되면 버튼을 반복해서 누르지 말고 원인을 해결한다.

### 운영 제어

운영 제어에서는 API, 웹, 워커 상태를 확인하고 워커를 시작/중지한다.

워커 시작 전 확인:

- API가 실행 중인지
- `WORKER_SECRET`이 API와 같은지
- `CODEX_WORKSPACE_ROOT`가 실제 앱 레포 경로인지
- 작업 디렉터리에 미커밋 변경이 없는지

워커가 시작되어도 실행이 실패하면 `.run/logs` 경로의 로그를 확인한다.

## 기록 > 감사 로그

### 목적

운영자가 수행한 주요 변경 이력을 확인한다.

### 감사 대상

- 직원 등록
- 라이선스 부여/회수
- 프로젝트 멤버 권한 변경
- GitHub 라벨 추가
- 작업 실행 생성
- 승인 처리
- 워커 재시도

### 확인 방법

1. 시간순으로 최근 이력을 확인한다.
2. 의도하지 않은 권한 변경이 있는지 본다.
3. 실패한 작업 앞뒤에 어떤 운영 작업이 있었는지 확인한다.
4. 필요하면 GitHub 이슈와 PR 링크를 함께 확인한다.

## 기록 > 시스템 설정

### GitHub 연결

GitHub 연결 상태에서 다음을 확인한다.

- 저장소가 `ryungwang/synub-teams-ai`인지
- 준비 라벨이 `codex-ready`인지
- 토큰이 설정되어 있는지
- 연결 상태가 정상인지

필수 환경변수:

```text
GITHUB_TOKEN
GITHUB_OWNER
GITHUB_REPO
GITHUB_READY_LABEL
```

### 로컬 서비스

로컬 서비스 상태에서 API, 웹, 워커 상태를 확인한다.

- API: Spring Boot 관리자 API
- 웹: React 운영 콘솔
- 워커: Codex 실행기

워커가 중지 상태여도 API와 웹은 정상 운영될 수 있다. 단, 실제 Codex 실행은 워커가 켜져 있어야 진행된다.

## 문제 해결

### GitHub 연결이 안 됨

확인할 것:

- `GITHUB_TOKEN`이 실제 값인지
- 토큰 권한에 Issues, Contents, Pull requests가 포함되어 있는지
- `GITHUB_OWNER`, `GITHUB_REPO`가 올바른지
- API를 재시작했는지

### `codex-ready` 동기화 후 작업이 안 생김

확인할 것:

- 이슈에 `codex-ready` 라벨이 있는지
- 이미 같은 이슈로 작업이 만들어졌는지
- 정보 부족 또는 테스트성 이슈로 차단되었는지
- API 로그에 GitHub 오류가 있는지

### 작업 실행 생성이 실패함

표시된 실패 메시지를 먼저 확인한다.

- 정보 부족: 이슈 본문에 재현 절차, 오류 메시지, 기대 동작을 보강한다.
- 테스트성: 실제 제품 오류 이슈로 다시 접수한다.
- 승인 필요: `승인 대기`에서 승인한다.
- 중복 실행: 기존 실행 결과를 확인한다.

### 재시도하면 로그인 페이지로 이동함

정상적인 정책 차단은 로그인 만료가 아니다. 최신 웹 빌드인지 확인하고, API 응답이 401인지 400/403인지 확인한다. 401이면 관리자 토큰을 다시 입력한다.

### 워커가 계속 실패함

확인할 것:

- 앱 레포 작업 디렉터리에 미커밋 변경이 있는지
- `CODEX_WORKSPACE_ROOT`가 올바른지
- `WORKER_SECRET`이 API와 같은지
- Codex CLI가 실행 가능한지
- GitHub push 권한이 있는지

## 운영 원칙

- 오류 제보 접수만으로 자동 수정하지 않는다.
- 정보가 부족한 이슈는 작업 실행하지 않는다.
- 테스트성 이슈는 작업 실행하지 않는다.
- 고위험 작업은 승인 후 실행한다.
- PR은 자동 병합하지 않는다.
- 토큰, 비밀번호, 고객 정보는 이슈와 로그에 남기지 않는다.
- 운영 방식이 바뀌면 이 문서와 체크리스트를 함께 갱신한다.
